# 项目总览

## 1. 项目定位

项目名为 `guess-ancient-chinese-people`，是一款由大语言模型担任考官的“猜历史人物”游戏。每局随机选择一名历史人物，玩家通过一般疑问句逐步排除候选人，模型原则上只允许回答：

1. `是。`
2. `否。`
3. `或许是。`
4. `或许不是。`
5. `无可奉告，换个问法吧。`

玩家猜中后，模型公布胜利与简短人物介绍；玩家投降后，模型公布答案；有效提问达到阈值后可以索要提示；对模型回答有疑问时，可输入“重答”“我怀疑”“你确定吗”等触发整段历史问答的批量复核。

## 2. 当前可用游戏模式

| 模式 | Streamlit 入口 | 标称人物数 | 审阅时实际加载数 | 主题 |
| --- | --- | ---: | ---: | --- |
| 全古代 1000 人 | `app.py` | 1000 | 1000 | 历史 |
| 全古代 200 人 | `app_03_mini.py` | 200 | 200 | 中国历史 |
| 明朝 200 人 | `app_03_ming.py` | 200 | 377 | 明朝历史 |

`app_03_01.py` 是 `app.py` 的完全重复副本，不参与单 EXE 启动器的运行时文件清单。

启动首页还展示春秋战国、秦汉、三国、盛唐以及欧洲各地区版本，但这些入口均被标记为研发中或编撰中，当前不可点击。

## 3. 当前主线能力

- 使用 Streamlit 提供聊天界面、侧栏 API 配置和状态调试面板。
- 支持智谱、DeepSeek、OpenAI、xAI 以及自定义 OpenAI 兼容端点。
- API Key 可从 Streamlit secrets、环境变量或页面手动输入获取。
- 用 `GameState` 管理目标人物、提问次数、阶段和提示历史。
- 将系统 Prompt 拆分为角色、状态、规则、提示、输出、事实核查、重答等模块。
- 将 200 名人资料结构化为 JSON，并向模型注入朝代、性别、身份、头衔、别称、生卒年和简介。
- 对网络错误、HTTP 429 和 5xx 实现最多 3 次指数退避重试。
- 对历史规范问答按每批 10 条调用模型复核。
- 提供 PyInstaller 单文件 EXE：启动一个本地首页，再为不同游戏模式派生 Streamlit 子进程。
- 保留早期 Dify 工作流、HTA 启动页和 v1/v2 Python 实现，便于追溯演进。

## 4. 技术栈

| 层次 | 技术 |
| --- | --- |
| 游戏 UI | Python、Streamlit |
| 启动首页 | HTML、CSS、原生 JavaScript |
| 本地启动服务 | `http.server.ThreadingHTTPServer` |

| 状态与数据 | `dataclasses`、JSON、Markdown、CSV |

运行依赖文件当前只列出：

- `streamlit>=1.30,<2.0`
- `requests>=2.28`
- `pyinstaller>=6.0`

数据转换脚本还需要 `openpyxl`，测试需要 `pytest`，但二者没有出现在依赖文件中。

## 5. 当前架构评价

项目最重要的进步是职责分层：

- 数值阈值和基础阶段进入 Python。
- Prompt 从单一长字符串拆成可组合模块。
- API 请求和重试从页面代码中抽离。
- 人物名单从纯姓名逐步升级为结构化事实。
- 打包入口与实际游戏进程分离。

但当前仍处于“部分确定性、部分 Prompt 驱动”的中间状态。文件和注释多次称 `fact_checker.py` 为“代码层判定”，实际上它并不解析当前问题、也不直接给出真值，只是把目标人物的结构化字段整体注入 Prompt。猜中、是否投降、回答是否符合事实等关键裁决仍由模型完成，Python 只做关键词预判和事后状态标记。

## 6. 仓库成熟度

从代码组织和测试看，核心逻辑已经具备可维护基础；从产品交付看，还需要解决凭证安全、人物池边界、跨局上下文、确定性规则、集成测试和文档同步问题。

适合将当前版本视为：

- 一个功能完整、可以本地运行和打包演示的 v3 原型；
- 一个继续向“规则引擎 + 可验证人物知识库 + 稳定桌面发行版”演进的基础；
- 尚不适合在不处理凭证与数据边界问题的情况下公开分发的最终版本。
