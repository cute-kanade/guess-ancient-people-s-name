# 现存问题与改进建议

以下问题按“优先处理、随后处理、长期演进”整理。它们是代码审阅结论，不代表已经在本次文档工作中修复。

## 1. 优先处理

### 1.1 仓库和启动首页中存在 API 凭证

现状：

- 多个 `legacy/*.py` 和早期 HTA 页面包含历史明文 Key。
- 当前 `frontend/index.html` 和部分 v3 HTA 使用固定 XOR 字符串“混淆”内置 Key。
- XOR 密钥与密文都随客户端分发，任何人都可以还原，不能视为加密。
- Git 历史中即使删除当前文件内容，旧凭证仍可能存在。

风险：

- 额度滥用和费用损失；
- 凭证持有者身份暴露；
- 公开发行的 EXE 可被静态提取；
- 用户误以为“已加密存储”。

建议：

1. 立即吊销和轮换所有曾进入仓库、HTA、HTML 或 EXE 的 Key。
2. 删除启动首页内置凭证逻辑，只接受用户输入、环境变量或操作系统安全凭证存储。
3. 用秘密扫描工具检查工作树和 Git 历史。
4. 若一定要提供演示额度，应由受控后端代理完成，并设置用户、速率、预算和来源限制。
5. 修改 UI 文案，不再把 XOR 称为加密。

### 1.2 明朝 200 人版实际加载 377 人

原因是 `load_people_from_csv()` 会把 JSON 独有人物追加到主题 CSV。明朝 CSV 与 JSON 仅重合 23 人，剩余 177 人全部被加入。

建议：

- 为主题池增加 `append_json_only=False`；
- 写回归测试断言明朝版恰好 200 人，且姓名集合等于明朝 CSV；
- 结构化数据只做同名覆盖，不改变主题池边界。

### 1.3 新开一局没有清空旧局消息

`GameState.reset()` 清空次数、阶段和提示历史，但 `st.session_state.messages` 保留。后续系统 Prompt 会携带新目标，同时历史里可能有旧目标、旧提示、旧胜利和旧投降内容。

后果：

- 模型可能混淆新旧人物；
- 重答可能扫描到上一局问答；
- 上下文持续增长，成本和延迟增加；
- 玩家界面无法清晰分局。

建议：

- 重开时清空消息，或把消息按 `game_id` 分组；
- 批量复核只扫描当前局；
- 如果需要保留 UI 历史，发送给模型时只取当前局消息。

### 1.4 关键裁决仍由模型控制

当前 Python 会计算提示阈值和关键词预判，但以下行为仍依赖模型：

- 玩家是否猜中；
- 是否应公布答案；
- 事实问题的“是/否”；
- 是否严格使用规范答案；
- 是否生成重复提示；
- 是否遵守胜利/投降格式。

`fact_checker.py` 只是注入事实，不是确定性判定器。模型输出后也没有规范化或拒绝不合规格式。

建议分阶段处理：

1. 用姓名和别称规范化做确定性猜中判断。
2. 投降和重玩由 Python 直接生成状态转换和固定回复框架。
3. 对朝代、性别、身份、头衔、生卒年等可结构化问题建立解析器。
4. 模型只处理模糊、解释性或资料缺失的问题。
5. 对普通回复做枚举校验；不合规时自动修复或低温重试。

## 2. 随后处理

### 2.1 “开始”使用任意子串匹配

任何包含“开始”的输入都会重开，例如“他什么时候开始做官”。提示、投降等元操作也会被计入 `dialogue_count`，与“有效提问次数”的文案不完全一致。

建议将命令解析改为：

- 对开局命令做去空白后的精确匹配或明确正则；
- 在增加次数前排除开局、重玩、投降、提示和怀疑；
- 为每类命令定义统一优先级。

### 2.2 阶段状态没有真正控制后续行为

胜利或投降后只是把温度从 0.3 改为 0.6，仍会用同一游戏 Prompt 与同一目标调用模型。注释称“暂时转为通用人工智能状态”，代码没有独立的一般聊天分支。

建议建立显式状态转移表：

| 当前阶段 | 普通问题 | 重玩 | 投降 | 猜中 |
| --- | --- | --- | --- | --- |
| PLAYING | 游戏问答 | 新局 | 结算 | 结算 |
| WON | 提示重玩或一般聊天 | 新局 | 忽略 | 忽略 |
| SURRENDERED | 提示重玩或一般聊天 | 新局 | 忽略 | 忽略 |

### 2.3 更换 API 配置可能不生效

启动器按脚本复用已运行子进程。用户第二次选择同一模式并换 Key、URL 或模型时，`streamlit_runner_port()` 会直接返回旧端口；旧进程继承的是第一次启动时的环境变量。

建议：

- 配置变化时重启对应子进程；
- 或把配置显式传入 Streamlit 会话，而不是依赖进程环境；
- 首页显示“已运行，配置未改变”或提供停止/重启按钮。

### 2.4 并发启动存在共享环境变量竞态

`ThreadingHTTPServer` 可并发处理请求，而 `/api/launch` 先修改全局 `os.environ`，再进入子进程锁。两个同时启动的请求可能相互覆盖 Key、URL 或模型。

建议不要修改全局环境，改为：

```python
env = os.environ.copy()
env["LLM_API_KEY"] = request_key
subprocess.Popen(..., env=env)
```

并把配置与脚本在同一个锁区间内处理。

### 2.5 健康检查不能可靠发现 Streamlit 脚本异常

启动器拉取 Streamlit 根 HTML 并搜索 `ModuleNotFoundError` 或 `Uncaught app execution`。现代 Streamlit 根页通常是静态壳，脚本错误通过后续会话通道呈现，因此 HTTP 200 不代表应用逻辑成功。

建议：

- 检查子进程是否提前退出；
- 读取日志中的启动成功或异常标记；
- 增加真正的应用健康端点或自动浏览器烟雾测试；
- 超时后在首页显示日志位置。

### 2.6 配置常量重复

`config.py` 和 `llm_client.py` 都定义温度、重试、超时、批量大小、默认 URL 和模型。未来只改一处会产生漂移。

建议 `llm_client.py` 全部从 `config.py` 导入，并使用 `APIConfig` 或删除未使用的数据类。

### 2.7 数据加载缺少验证与可观测性

- JSON 坏数据会直接抛错。
- CSV 非编码异常被静默吞掉。
- 姓名重复、空值、类型错误没有报告。
- 相对路径要求工作目录正确。

建议引入 Schema 校验、明确异常信息、启动时数据统计，并以 `__file__` 或资源根解析路径。

## 3. 文档与仓库维护

### 3.1 根 README 过时

根 `README.md` 仍说明运行 `app_01_02.py`，但文件已移入 `legacy/`，也没有介绍 v3、三套模式、环境变量、测试或 EXE。

### 3.2 Prompt 文档停留在 v2

`prompts/md/README.md` 仍把 `app_02_01.py` 写成入口，未覆盖事实注入和批量重答。建议由源码注释生成或在改 Prompt 时同步测试与文档。

### 3.3 历史入口失效

- `旧版.bat` 指向不存在的根文件。
- exe_01/02 HTA 指向已移入 `legacy/` 的脚本。
- 普通 `.html` 中的 ActiveX 启动方式在标准浏览器不可用。
- 某些历史 HTA 的 API URL/模型表单并未真正传给子进程。

建议把历史入口集中放到 `legacy/launchers/`，添加“仅供归档、不可直接运行”的说明。

### 3.4 仓库包含本机信息快照

`t` 暴露作者邮箱、本机 Git 安装位置和配置来源；`.obsidian/workspace.json` 记录大量已经不存在的本机工作文件。

建议移除无关快照，把 Obsidian 工作区 UI 状态加入忽略，仅保留真正需要共享的编辑器配置。

### 3.5 文件编码和命名

- `build_exe.bat` 中文乱码。
- 两个 CSV 使用 GBK，而大部分代码和文档使用 UTF-8。
- `.xls` 实际是 `.xlsx`。
- 中英文和版本命名并不统一。

建议统一 UTF-8、统一版本策略，并把运行入口控制在少数稳定文件。
