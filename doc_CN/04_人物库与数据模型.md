# 人物库与数据模型

## 1. `Person` 模型

```python
Person(
    name: str,
    dynasty: str | None,
    gender: str | None,
    identity: list[str],
    titles: list[str],
    aliases: list[str],
    year_birth: int | None,
    year_death: int | None,
    summary: str | None,
)
```

除姓名外，其余字段都允许缺失。缺失字段不会生成事实提示，问题会交给模型依据自身知识判断。

## 2. 三类数据源

### 2.1 1000 人 Markdown

`peoples_names.md` 使用：

```text
1. 黄帝
2. 炎帝
...
1000. 王朗
```

审阅结果：

- 非空记录 1000 条；
- 解析后姓名 1000 个；
- 姓名唯一；
- `_parse_md()` 会去掉序号和点号；
- 只有 200 人能从 JSON 获得结构化信息，其余约 800 人只有姓名。

没有逐条阅读或考据这 1000 个名字。

### 2.2 两个 200 人 CSV

两个 CSV 都是 GBK/ANSI 系列编码，`people_db._parse_csv()` 会按以下顺序尝试：

```text
utf-8 → utf-8-sig → gbk → gb2312 → gb18030
```

全古代 CSV：

- 200 条；
- 200 个唯一姓名；
- 列为“序号、人名”。

明朝 CSV：

- 200 条；
- 200 个唯一简体姓名；
- 列为“序号、简体人名、繁体人名”；
- 当前程序只读取简体姓名。

### 2.3 结构化 JSON

`data/people.json` 审阅时有 200 条、200 个唯一姓名，并且姓名集合与全古代 200 人 CSV 完全一致。

字段覆盖统计：

| 字段 | 非空人数 | 覆盖率 |
| --- | ---: | ---: |
| dynasty | 200 | 100% |
| gender | 200 | 100% |
| identity | 200 | 100% |
| titles | 75 | 37.5% |
| aliases | 168 | 84% |
| year_birth | 153 | 76.5% |
| year_death | 177 | 88.5% |
| summary | 200 | 100% |

这些统计只说明字段是否存在，不代表内容已经逐条完成史实校验。

## 3. 当前合并算法

### 3.1 1000 人版

`load_people()`：

1. 用 Markdown 作为基础顺序和全集。
2. 同名 JSON 人物替换 Markdown 的姓名占位记录。
3. JSON 中有、Markdown 中没有的人追加到末尾。

当前 JSON 的 200 人均包含在 1000 人名单中，所以最终仍是 1000 人，其中 200 人有结构化信息。

### 3.2 全古代 200 人版

`load_people_from_csv()`：

1. 用 CSV 作为基础。
2. 同名 JSON 人物替换 CSV 占位记录。
3. JSON 独有人物追加到末尾。

由于 JSON 与全古代 CSV 的姓名集合正好相同，最终仍是 200 人，且全部有结构化信息。

### 3.3 明朝 200 人版

明朝 CSV 与通用 JSON 只有 23 个姓名重合。合并时：

- 200 个明朝 CSV 人物保留；
- 23 个重合人物被 JSON 结构化记录替换；
- JSON 余下 177 人被追加。

因此：

```text
200 + (200 - 23) = 377
```

“明朝 200 人版”实际会随机到大量不属于明朝限定名单的人物。这是当前最明确的数据逻辑错误。

## 4. 事实注入方式

每次正常问答前，目标人物的全部已知结构化字段会拼成类似：

```text
【目标人物确定性事实】
- 朝代：宋
- 性别：男
- 身份：文学家、词人
- 固定头衔/并列称谓：唐宋八大家
- 别称：号东坡居士
- 生卒年：1037–1101
- 简介：北宋文学家……
```

然后发送给模型。当前不会：

- 根据本轮问题只选择相关字段；
- 用程序比较问题中的朝代、性别或身份；
- 检查玩家输入的人名别称是否等于目标；
- 从结构化字段直接生成“是/否”；
- 标记资料来源、置信度或争议事实。

## 5. 数据完整性与格式问题

### 5.1 JSON 缺少 Schema 验证

`_load_json()` 默认每项都有 `name`，并假定字段类型正确。JSON 语法错误、缺少姓名、年份为字符串、列表字段写成字符串等情况会导致崩溃或产生异常 Prompt。

### 5.2 人名没有统一规范化

同名匹配是精确字符串匹配，没有处理：

- 繁简转换；
- 空格与异体字；
- 帝号、庙号、姓名、字、号之间的等价；
- 常见别称；
- 重名人物和时代消歧。

`aliases` 仅被展示给模型，没有用于 Python 层判断玩家是否猜中。

### 5.3 CSV 解析错误被静默吞掉

编码错误会尝试下一编码，这是合理的；但其他异常也被 `except Exception: continue` 静默忽略，最终只返回空列表，不利于定位列名错误、坏行或文件权限问题。

### 5.4 XLS 扩展名与真实格式不一致

`peoples_names.xls` 的文件头为 `PK\x03\x04`，实际是 XLSX ZIP 容器。`convert_to_xls.py` 使用 `openpyxl` 也会生成 XLSX。建议把文件和脚本目标名改为 `.xlsx`。

### 5.5 结构化事实需要来源和审校流程

目前 JSON 中没有：

- 信息来源；
- 最后校验日期；
- 字段级置信度；
- 有争议说法；
- 适用问题标签。

若目标是降低模型事实错误，建议为结构化字段增加可追踪来源，并为高频问题建立人工验证测试样例。

## 6. 推荐的数据加载语义

建议显式区分两种 API：

```python
load_people_pool(base, enrichment, append_unknown=False)
load_people_catalog(base, enrichment, append_unknown=True)
```

游戏主题池应使用 `append_unknown=False`，确保人物只能来自对应名单；数据管理或总目录场景才使用 `append_unknown=True`。
